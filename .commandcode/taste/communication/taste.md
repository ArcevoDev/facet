# Communication
- Prefers concise, direct go-ahead signals (e.g., "sure - proceed...", or simply "continue" to resume leftover work from a prior session) when satisfied with a proposed plan: trusts the assistant to execute the full plan without micromanaging or requiring per-step re-approval. Avoids verbose confirmation cycles when the direction is already clear; a terse imperative like "run - node gen-snapshot.js ... commit our changes and push to main branch.... then publish our package..." delegates the whole sequence in one line. A bare "continue" is also expected to carry the design decisions already agreed in earlier discussion ("continue... don't forget our signin state machine diagram or flowchart... we discussed..") : those decisions are commitments to be remembered and delivered, not topics to re-open. Re-confirmed when "continue..." alone resumed a tracked priority list (P3 CLI smoke test) from the .agent tracker with no further direction, and again when "continue.." (with only an IDE file context, no restated spec) resumed in-flight crash-recovery work — the bare signal is expected to carry all prior decisions and reconstruction plans forward. Confidence: 0.97
- Dislikes AI-sounding marketing copy: explicitly flags em dashes (":"), boilerplate descriptions, and generic "from zero to production" phrasing as "AIish." Prefers natural, human-sounding copy that avoids patterns typical of AI-generated promotional text. Applies to landing pages, READMEs, and any public-facing documentation. Emdashes are banned repo-wide as an explicit style rule ("purge emdash everywhere"): the emdash character (—) must not appear in any source copy or code, with commas, colons, or other punctuation used instead. Explicitly re-affirmed when the user had to manually strip emdashes the assistant had added to docs-page lines and restated the rule: "Emdashes (—) are not allowed in docs pages or any copy." Confidence: 0.95
- Wants the assistant to confirm the actual root cause of a reported error before fixing it ("confirm and fix"): diagnose with concrete evidence (files on disk, running processes, resolution paths), apply the fix, and verify the fix end-to-end before reporting done : rather than jumping to a speculative fix or churning config. Re-affirmed when a pasted CI log overturned the documented theory (AGENTS.md said the old publish job died on "repo-fetch errors", but the log showed the real cause was a missing `permissions: contents: write` block producing a 403 push denial) — pasted evidence can and should override stale docs about what broke. Confidence: 0.75
- When the user says the assistant has been "debugging the wrong work" and restates the actual problem, pivot immediately to the user's stated symptoms and treat the restatement as authoritative : do not keep iterating on the prior hypothesis (the assistant burned many steps on a stale-build/overlap theory before the user clarified the real issue: topbar content misplaced into the page body and no `<Outlet />` rendering). Confidence: 0.6
- Defects are reported by the visual symptom, not the root cause: the user describes what renders wrong (e.g., "the accordion is displaying all its variants in the grid") and expects the assistant to investigate and find the cause (e.g., an over-eager preview component) : symptom-first reporting, not diagnosis. Confidence: 0.75
- Prefers multi-part questions answered in single concise lines ("write in single lines") rather than long prose sections: each question gets a one-line verdict/bullet, with detail available on request. Confidence: 0.6
- Decision questions are asked with the user's own lean ("should we delete the deploy and leave it as our internal docs... or leave the storybook deploy"), or as an open "do you think we should X" opinion ask ("do you think we should put our navbar in that page also", "do we leave as is or remake like we did github in our registry"): expects a recommendation with rationale, not just an options recap. Re-affirmed when the user asked whether facet component styles needed updating "or you think its fine as-is" and expected a deferral verdict, not an options recap. Confidence: 0.76
- When the user signals doubt about whether they communicated ("i dont know if i am communicating"), confirm understanding by restating the requirement back before implementing ("You're communicating clearly — I get it: ..."), then proceed with the restated spec as the contract. Confidence: 0.55
- When the assistant offers equivalent workflow options and asks the user to choose, the user defers the decision back to the assistant ("whichever is best...") and expects it to pick the option that leaves the least manual work for them — here, running `changeset version`, verifying the build against the bumped versions, and committing so the user's release becomes a single `pnpm changeset publish` — then execute that choice fully without re-asking. Re-affirmed when the user delegated landing routing decisions the same way ("we could even adjust or reshape the routings... whichever is best..."). Confidence: 0.6
- Bug reports arrive with reproduction evidence pasted verbatim: the exact command the user ran and its raw output (e.g., `node scripts/gen-icon-map.mjs` → "Wrote icon-map.ts (1763 icons)"), followed by the user's own tentative hypothesis about the cause ("maybe it is also deprecated...") — the pasted command/output is authoritative context to work from, while the hypothesis is a lead to confirm or refute with on-disk evidence, not a directive or an established fact. Confidence: 0.5
- Before resuming or finishing in-flight work, wants half-finished/uncommitted changesets cross-checked against the project's documented rules (e.g., AGENTS.md CI contract) and the declared dependency surface (deps declared but never imported, keyframes/theme vars referenced but not defined) — discrepancies are surfaced as deliberate-decision points rather than silently resolved. Confidence: 0.5
- A reversal clause appended to a proceed signal ("continue.. that was a mistake..") right after a change was executed is an undo directive for that change, not a throwaway aside: when the user says a just-performed change (here: removing the overlay sidebar mode) "was a mistake," they expect the assistant to identify which change is being reversed and revert/reconsider it before continuing — treating it as a pure continue signal and pressing on with the removal was a miss. Confidence: 0.5
- Terse planning prompts like "whats next..." delegate next-step determination entirely to the assistant: the expected response is to consult the local tracker plus git/repo state, summarize what's outstanding (separating done/committed from open), and propose a prioritized pick with rationale — not to bounce the question back to the user. Confidence: 0.5
- When reporting what's open, the accounting must be EXHAUSTIVE: a single-item answer to "what's still open" gets challenged ("are you sure item 13 is the only thing this repo needs to checkout..."), so the assistant must enumerate every outstanding item — the blocking steps for the current batch (e.g., unwritten changeset, uncommitted work) plus each deferred backlog item (CI publish, tree-shakeable icons, chunk-size warnings) — not just the headline item that was already known. Confidence: 0.6
