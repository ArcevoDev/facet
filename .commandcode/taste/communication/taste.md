# Communication
- Prefers concise, direct go-ahead signals (e.g., "sure - proceed...", or simply "continue" to resume leftover work from a prior session) when satisfied with a proposed plan: trusts the assistant to execute the full plan without micromanaging or requiring per-step re-approval. Avoids verbose confirmation cycles when the direction is already clear; a terse imperative like "run - node gen-snapshot.js ... commit our changes and push to main branch.... then publish our package..." delegates the whole sequence in one line. A bare "continue" is also expected to carry the design decisions already agreed in earlier discussion ("continue... don't forget our signin state machine diagram or flowchart... we discussed..") : those decisions are commitments to be remembered and delivered, not topics to re-open. Re-confirmed when "continue..." alone resumed a tracked priority list (P3 CLI smoke test) from the .agent tracker with no further direction. Confidence: 0.95
- Dislikes AI-sounding marketing copy: explicitly flags em dashes (":"), boilerplate descriptions, and generic "from zero to production" phrasing as "AIish." Prefers natural, human-sounding copy that avoids patterns typical of AI-generated promotional text. Applies to landing pages, READMEs, and any public-facing documentation. Emdashes are banned repo-wide as an explicit style rule ("purge emdash everywhere"): the emdash character must not appear in any source copy or code, with commas, colons, or parentheses used instead. Confidence: 0.9
- Wants the assistant to confirm the actual root cause of a reported error before fixing it ("confirm and fix"): diagnose with concrete evidence (files on disk, running processes, resolution paths), apply the fix, and verify the fix end-to-end before reporting done : rather than jumping to a speculative fix or churning config. Confidence: 0.7
- When the user says the assistant has been "debugging the wrong work" and restates the actual problem, pivot immediately to the user's stated symptoms and treat the restatement as authoritative : do not keep iterating on the prior hypothesis (the assistant burned many steps on a stale-build/overlap theory before the user clarified the real issue: topbar content misplaced into the page body and no `<Outlet />` rendering). Confidence: 0.6
- Defects are reported by the visual symptom, not the root cause: the user describes what renders wrong (e.g., "the accordion is displaying all its variants in the grid") and expects the assistant to investigate and find the cause (e.g., an over-eager preview component) : symptom-first reporting, not diagnosis. Confidence: 0.75
- Prefers multi-part questions answered in single concise lines ("write in single lines") rather than long prose sections: each question gets a one-line verdict/bullet, with detail available on request. Confidence: 0.6
- Decision questions are asked with the user's own lean ("should we delete the deploy and leave it as our internal docs... or leave the storybook deploy"), or as an open "do you think we should X" opinion ask ("do you think we should put our navbar in that page also", "do we leave as is or remake like we did github in our registry"): expects a recommendation with rationale, not just an options recap. Confidence: 0.7
- When the user signals doubt about whether they communicated ("i dont know if i am communicating"), confirm understanding by restating the requirement back before implementing ("You're communicating clearly — I get it: ..."), then proceed with the restated spec as the contract. Confidence: 0.55
- Bug reports arrive with reproduction evidence pasted verbatim: the exact command the user ran and its raw output (e.g., `node scripts/gen-icon-map.mjs` → "Wrote icon-map.ts (1763 icons)"), followed by the user's own tentative hypothesis about the cause ("maybe it is also deprecated...") — the pasted command/output is authoritative context to work from, while the hypothesis is a lead to confirm or refute with on-disk evidence, not a directive or an established fact. Confidence: 0.5
